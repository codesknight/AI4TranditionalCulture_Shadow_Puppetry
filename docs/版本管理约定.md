# 版本管理约定

## 仓库与分支

- 远程仓库：https://github.com/codesknight/AI4TranditionalCulture_Shadow_Puppetry
- 默认分支：`main`，保留经过检查的可用内容。
- 独立功能使用 `feat/简短主题`；修复使用 `fix/简短主题`；较大文档更新使用 `docs/简短主题`。分支名建议使用英文与短横线。
- 小范围文档更新可直接提交；涉及多人协作或较大改动时，推送工作分支并通过 Pull Request 审阅合并。

## 日常工作

开始修改前检查工作区并同步。若有未提交改动，先妥善提交或暂存，再拉取远程内容。

```bash
git status
git switch main
git pull --ff-only
git switch -c feat/your-topic
```

完成一组相关改动后，检查差异，只暂存此次需要提交的文件：

```bash
git diff
git add README.md
git diff --cached
git diff --cached --check
git commit -m "docs: 更新项目说明"
git push -u origin HEAD
```

上面的文件名与分支名是示例，应按实际改动替换。已配置上游分支后，后续可直接运行 `git push`。

## 提交约定

使用 `类型: 具体内容`，例如：

- `docs: 补充皮影戏历史资料来源`
- `feat: 增加影人展示功能`
- `fix: 修复影人关节定位错误`
- `chore: 更新项目忽略规则`

每次提交尽量只解决一个明确问题，便于审阅和回退。不要对共享分支强制推送；撤销已共享的提交时，优先使用 `git revert <提交编号>` 生成可追溯的撤销记录。

## 提交前检查

- 文档链接与资料来源可追溯，传说、推测与可核实事实有明确区分。
- 不提交密码、访问令牌、真实 `.env` 文件与私人信息；`.gitignore` 无法自动清除已跟踪的敏感文件。
- 不提交依赖目录、缓存和临时产物。
- 图片、录音、视频和剧本等素材记录来源及授权；大型素材先确定存储方案，避免直接进入普通 Git 历史。
- 修改代码后运行 `npm run verify`，包含格式、语法与资源引用检查、自动测试及静态构建。推送与 PR 也会触发 GitHub Actions 检查。
- 每轮开发同步维护 `docs/logs` 中相关需求、开发、测试与缺陷记录；未执行的验证明确写为待完成。

发布版本时再创建有实际意义的版本标签，例如 `v0.1.0`；日常资料更新无需逐次打标签。
